## 架构选择：DCC 负责创作状态，服务端负责生成环境

模型、依赖和 GPU runtime 留在远程服务；Maya 只承载动画师需要直接操作的状态。公开层面的数据流可以压缩为：

```text
Maya Prompt + Constraint Timeline
              │
              ▼
      remote generation service
              │
              ▼
 four candidates + canonical authoring motion
              │
              ▼
   choose one → Active Motion → export
```

这个边界有两个目的。第一，动画师不需要在工作站安装模型训练栈；第二，场景内的 Prompt、Locator、pose snapshot 与选中候选仍由 Maya 管理。网络任务可以异步排队、恢复或失败，但不能让 UI 在未知状态下继续提交第二个任务。

界面因此围绕一个主状态机组织，而不是让多个 Tab 各自改变 scene：

```text
Ready → Generating → Choosing Candidate → Active Motion
  ▲                                      │
  └──────────── edit constraints ────────┘
```

## Constraint Timeline 不是装饰层

Timeline 同时承载连续 Prompt 段、duration、Root path、左右手脚 end-effector 与 FullBody pose。关键决定是把 Maya scene data 作为 authoring 真值，而不是让嵌入式网页维护一份不可见的副本。

- Root Locator 是路径数据；Curve 只是由 Locator 派生的显示。
- Hand / foot / FullBody 保存的是明确帧上的 snapshot，不会随着 Control 后续移动而偷偷变化。
- Timeline 拖动改变目标时间；只有显式“重新采样”才更新姿态内容。
- 保存 scene 后，Prompt、约束、playhead、候选 lineage 与 Active Motion 状态可以一起恢复。

FullBody 编辑尤其需要 transaction。进入编辑时先保存当前 authoring state；用户可以移动 Joint 或 IK Control，再显式 Save 或 Cancel。生成按钮在事务未结束时保持不可用，避免把半编辑姿态提交给远程任务。

<Callout type="takeaway" title="可见状态比按钮数量更重要">
  生成工具的危险状态通常不是模型报错，而是用户不知道当前操作会覆盖什么。把 editing、generating、choosing 与 active 明确分开后，异步任务和 Maya scene 才有可解释的恢复路径。
</Callout>

## 四候选之后，只保留一个 Active Motion

每次生成返回四个候选。Maya 同时展示它们，让用户通过 Viewport mesh 或候选卡完成一次明确选择。被选动作成为唯一 Active Motion，场景中的其余候选 DAG 被移除；候选 lineage 仍被保留，必要时可以恢复比较，而不必重新运行模型。

这里有一条容易被误解的边界：Active Motion 是观察、Constraint 捕获和迭代来源，**不是**下一轮 KIMODO 的 motion-to-motion conditioning。重新生成时传入的是当前 Prompt、duration 与显式 constraints；来源 Job/Candidate 只进入 lineage。

## 为什么 FBX world rotation 不能当 authoring contract

早期版本曾把候选 FBX 的 world rotation 复制到 Maya authoring rig。这个路径看似直接，实际把不同的 bone axis、rest basis 与 pre-rotation 当成了相同坐标系，结果可能是身体折叠、旋转失真，以及与 IK graph 相关的 bake 警告。

最终方案让服务端为每个候选额外写出 canonical SOMA77 authoring motion：

- 固定 Joint 顺序与 parent index；
- Root 使用 centimeter translation；
- 每帧使用 normalized local quaternion；
- 附带 frame rate、coordinate-system version、Skeleton hash 与完整性校验；
- 写出前用 forward reconstruction 检查 posed-joint error。

Maya 校验 schema、hash、帧数与 quaternion 后，直接把 Root translation 和 77 个 Joint local rotations 写成 animation curves。这条路径不依赖 `parentConstraint`、`orientConstraint` 或 `bakeResults()`。没有 canonical authoring motion 的旧任务仍可预览和导出原始资产，但不能安全地成为可继续编辑的 Active Motion。

<Callout type="finding" title="预览格式与编辑格式应该分开">
  FBX 适合交换与交付，却不是无损的内部 authoring state。保留 canonical local rotations 作为编辑契约，再把验证过的候选 FBX 作为交付资产，能把坐标约定和 export 职责拆开。
</Callout>

## Export 是最后一步，不是自动完成项目角色落地

导出会复制被选候选对应的、已经过 manifest 与 checksum 校验的原始 FBX，并允许用 Maya 原生保存流程命名。标准交付仍是 SOMA77 motion；项目角色的 Retarget、HumanIK、Skeleton Mapping、接触修整与 UE import 是下游任务，不属于本 case study 已验证的自动化范围。

换句话说，这里完成的是：

```text
KIMODO → SOMA77 authoring / exchange asset → DCC handoff
```

而不是：

```text
KIMODO → arbitrary project character → production-ready UE animation
```

## Release evidence：0.5.3 与 0.5.4 证明的不是同一件事

| 版本 | 已记录证据 | 不能据此声称 |
|---|---|---|
| 0.5.3 | Timeline typecheck/build、Python contract tests、完整 archive contract，以及 Maya 2024 QtWebEngine 双向 Bridge diagnostic | 动画师 pilot、团队采用、任意 Maya 环境兼容 |
| 0.5.4 | 可选 authentication mode compatibility、相关 automated coverage、当前 release archive hash | 新一轮 Maya 2024 interactive smoke、production readiness |

`0.5.4` 是当前 package，但它主要改变连接鉴权兼容性。最强的 Maya 2024 interactive diagnostic 仍来自 `0.5.3`。版本号更高不等于验证范围自动扩大，这也是本文把 release contract 与用户试点证据分开记录的原因。

## 当前结论

这套系统已经证明一个受限但完整的 DCC-native loop 可以工作：动画师在 Maya 表达 Prompt 与约束，远程服务生成四候选，canonical local quaternion 负责安全编辑，Active Motion 负责后续迭代，最终以经过验证的交换资产 handoff。

它还没有证明团队级生产成熟度。下一阶段真正需要的不是继续增加按钮，而是动画师 pilot、项目角色 Retarget 验收、失败恢复演练，以及逐篇完成代码、模型、DCC 组件与生成输出的 rights review。在这些 gate 完成前，本文保持 draft。
